# JVM 垃圾收集与内存分配易混点整理

本文整理学习 JVM 垃圾收集器、GC Roots、分代内存、G1/CMS 流程、对象晋升和 Full GC 时容易混淆的点。

## 1. GC Roots 是什么

GC Roots 可以理解为：

> 垃圾回收判断对象是否存活时的“起点引用”。

JVM 判断一个对象是不是垃圾，不是看它有没有被其他对象引用，而是看：

```text
从 GC Roots 出发，能不能沿着引用链找到这个对象。
```

如果能找到，说明对象还可能被程序使用，不能回收。

如果找不到，说明这个对象已经和程序执行入口断开联系，可以被回收。

例如：

```text
GC Roots -> A -> B -> C
```

`A、B、C` 都是存活对象。

再看：

```text
X <-> Y
```

`X` 和 `Y` 虽然互相引用，但如果 GC Roots 找不到它们，它们仍然是垃圾，可以被回收。

常见 GC Roots 包括：

- 虚拟机栈中引用的对象，例如方法参数、局部变量、临时变量。
- 类静态属性引用的对象，例如 `static User user`。
- 常量引用的对象，例如字符串常量池中的引用。
- Native 方法引用的对象。
- JVM 内部引用的对象，例如 `Class` 对象、类加载器、常驻异常对象等。
- 被 `synchronized` 锁持有的对象。

一句话记忆：

> GC Roots 是判断对象是否存活的入口；能从入口走到的对象是活对象，走不到的对象是垃圾。

## 2. 用户线程和 GC 线程

可以简单理解为：

```text
用户线程：执行程序业务代码的线程。
GC 线程：执行垃圾回收工作的线程。
```

例如，用户线程执行：

```java
User user = new User();
userService.save(user);
list.add(user);
```

GC 线程执行：

```text
标记存活对象
清理垃圾对象
复制对象
整理内存
```

当发生 Stop The World 时，用户线程会暂停，GC 线程进行垃圾回收。

## 3. 新生代和老年代

Java 堆通常可以粗略分成：

```text
Java 堆
├── 新生代
└── 老年代
```

### 3.1 新生代

新生代主要存放刚创建不久的对象。

大多数对象刚创建时，优先进入新生代的 Eden 区。

新生代特点：

```text
对象创建频繁
大多数对象很快死亡
Minor GC 发生频繁
```

新生代通常使用复制算法，因为新生代里真正存活下来的对象较少，复制成本相对低。

### 3.2 老年代

老年代主要存放存活时间较长的对象。

如果一个对象经历多次 Minor GC 后仍然存活，它可能会晋升到老年代。

老年代特点：

```text
对象相对稳定
死亡比例较低
一次回收成本更高
```

常见容易进入老年代的对象：

- 长期缓存对象。
- 单例对象。
- 静态集合引用的对象。
- 多次 Minor GC 后仍然存活的对象。
- 大对象。

对象大致流动过程：

```text
Eden -> Survivor -> 老年代
```

## 4. Parallel Scavenge 收集器和吞吐量

Parallel Scavenge 是一个新生代收集器。

它的特点：

```text
新生代收集器
多线程收集
使用复制算法
关注吞吐量
```

吞吐量公式：

```text
吞吐量 = 运行用户代码的时间 / 总运行时间

总运行时间 = 运行用户代码的时间 + GC 时间
```

例如：

```text
程序总运行 100 秒
用户代码运行 98 秒
GC 花费 2 秒

吞吐量 = 98 / 100 = 98%
```

Parallel Scavenge 被称为“吞吐量优先收集器”，意思是它更关注：

```text
整个程序运行过程中，GC 时间占比尽量低。
```

它不是单纯追求每一次 GC 停顿最短。

例如：

```text
方案 A：
每次 GC 停顿 20ms
GC 发生 100 次
总 GC 时间 = 2000ms

方案 B：
每次 GC 停顿 100ms
GC 发生 5 次
总 GC 时间 = 500ms
```

如果关注单次停顿，方案 A 更好。

如果关注整体吞吐量，方案 B 更好。

Parallel Scavenge 更偏向方案 B：允许某次停顿稍长，但希望整体 GC 时间占比更低。

### 4.1 Parallel Scavenge 和 ParNew 的区别

二者相似点：

```text
都是新生代收集器
都是多线程收集
都使用复制算法
```

主要区别在优化目标：

```text
ParNew：更关注单次 GC 停顿时间。
Parallel Scavenge：更关注整体吞吐量。
```

所以它们虽然都是在控制 GC 行为，但目标不同。

## 5. CMS 收集器

CMS 全称：

```text
Concurrent Mark Sweep
```

CMS 是一款老年代收集器，目标是尽量缩短用户线程停顿时间。

CMS 主要流程：

```text
初始标记 -> 并发标记 -> 重新标记 -> 并发清除
```

### 5.1 初始标记

初始标记只标记 GC Roots 能直接关联到的对象。

这个阶段需要 Stop The World，但速度较快。

### 5.2 并发标记

并发标记从 GC Roots 开始进行可达性分析，继续沿着引用链向下扫描。

这个阶段 GC 线程和用户线程可以一起运行。

问题是：用户线程还在运行，就可能修改对象引用关系。

例如原来：

```text
GC Roots -> A -> B
```

并发标记过程中，用户线程可能执行：

```java
A.b = null;
```

此时引用关系变成：

```text
GC Roots -> A
B 暂时不可达
```

因为用户线程一直在改引用关系，所以并发标记得到的结果可能不完全准确。

### 5.3 重新标记

重新标记的作用是：

> 修正并发标记期间，因为用户线程继续运行而产生变化的那部分标记记录。

它不是从头完整标记一遍，而是做补漏和修正。

重新标记需要 Stop The World。

原因是如果用户线程还继续运行，引用关系还会继续变化，GC 线程就很难得到稳定结果。

简单理解：

```text
并发标记：一边运行程序，一边大范围扫描对象关系。
重新标记：暂停一下，把刚才可能漏掉或变动的地方修正好。
```

### 5.4 并发清除

并发清除会清理已经被判定为垃圾的老年代对象。

这个阶段 GC 线程和用户线程可以一起运行。

因为 CMS 是老年代收集器，所以这里清理的是老年代垃圾，而不是新生代垃圾。

## 6. CMS 的吞吐量低

CMS 的优点是低停顿。

但 CMS 为了减少用户线程停顿，会让 GC 线程和用户线程并发执行。

并发执行的问题是：

```text
CPU 资源有限
用户线程要用 CPU
GC 线程也要用 CPU
```

所以用户线程虽然没有被长时间暂停，但它会和 GC 线程抢 CPU，导致业务代码运行速度下降。

例如：

```text
某个任务本来 10 秒完成。

使用 CMS 后：
GC 停顿时间可能很短，只有 0.1 秒。
但 GC 后台并发运行，占用 CPU，导致用户代码变慢。
最终任务可能 11 秒才完成。
```

所以 CMS 的问题不是“停顿时间一定长”，而是：

```text
停顿短，但 GC 后台工作会消耗 CPU，可能导致整体吞吐量下降。
```

一句话记忆：

> CMS 用后台并发 GC 换取低停顿，但后台 GC 也要吃 CPU，所以整体吞吐量可能降低。

## 7. CMS 的浮动垃圾

浮动垃圾指：

> CMS 并发回收期间，用户线程继续运行而新产生的、这一轮来不及清理的垃圾。

CMS 的并发清除阶段是：

```text
GC 线程正在清理垃圾
用户线程还在继续运行
```

用户线程继续运行时，可能继续创建对象，也可能让一些对象变成垃圾。

这些在本轮标记结束后才变成垃圾的对象，CMS 本轮不会回头再清理，只能等下一次 GC。

这些对象就是浮动垃圾。

### 7.1 浮动垃圾和老年代快满的关系

CMS 是老年代收集器，它清理的是老年代。

如果老年代快满了才开始 CMS，会有风险。

因为 CMS 回收过程中：

```text
用户线程还在运行
还可能继续产生浮动垃圾
新生代对象也可能晋升到老年代
```

这些都需要占用老年代空间。

如果老年代没有预留足够空间，可能出现：

```text
CMS 还没清理完
老年代已经没有足够空间
```

这就可能触发：

```text
Concurrent Mode Failure
```

然后 JVM 可能临时启用 Serial Old 进行老年代回收，停顿时间会更长。

一句话记忆：

> CMS 不能等老年代快满才启动，因为并发回收期间还会产生浮动垃圾，并且可能有新生代对象晋升到老年代。

## 8. G1 收集器的并发标记和最终标记

G1 运行过程中的几个关键步骤：

```text
初始标记 -> 并发标记 -> 最终标记 -> 筛选回收
```

这里容易混淆的是中间两步：

```text
并发标记
最终标记
```

### 8.1 并发标记

并发标记的主要任务是：

```text
从 GC Roots 出发，进行可达性分析，扫描对象图。
```

它要判断：

```text
哪些对象还活着
哪些对象可以回收
哪些 Region 垃圾较多，值得回收
```

这个阶段用户线程还在运行，所以引用关系可能发生变化。

### 8.2 SATB 是什么

SATB 全称：

```text
Snapshot At The Beginning
```

可以理解为：

> 在并发标记开始时，G1 逻辑上拍了一张对象引用关系的快照。

如果用户线程在并发标记期间修改了引用，G1 会通过 SATB 记录某些变化，避免漏标对象。

例如原来：

```text
A -> B
```

后来用户线程执行：

```java
A.b = null;
```

如果 GC 还没来得及扫描到 `B`，`B` 可能被漏标。

为了避免这种情况，SATB 会记录：

```text
A 曾经引用过 B
```

### 8.3 最终标记

最终标记的主要任务是：

```text
暂停用户线程，处理并发标记阶段遗留下来的少量 SATB 记录。
```

最终标记不是重新完整扫描一遍对象图。

它主要是把并发标记期间积累的记录处理完，修正最终标记结果。

### 8.4 并发标记和最终标记的区别

二者都和 SATB 有关，但功能不同：

```text
并发标记：
大范围扫描对象图，同时记录用户线程修改引用时产生的 SATB 记录。

最终标记：
暂停用户线程，集中处理剩余 SATB 记录，完成最终修正。
```

简单类比：

```text
并发标记 = 老师一边点名，班长一边记录谁在走动。
最终标记 = 让大家暂停一下，老师核对班长的小本子。
```

一句话记忆：

> 并发标记负责大范围扫描和收集变化；最终标记负责暂停后处理剩余记录并修正结果。

## 9. 对象优先在 Eden 分配

大多数对象刚创建时，会优先分配到新生代 Eden 区。

当 Eden 区空间不够时，JVM 通常会触发一次 Minor GC。

Minor GC 后：

```text
死亡对象被回收
存活对象进入 Survivor 区
部分对象可能晋升到老年代
```

## 10. 大对象直接进入老年代

大对象指需要大量连续内存空间的 Java 对象。

典型例子：

```text
很长的字符串
很大的数组
```

大对象可能直接进入老年代。

原因是新生代通常使用复制算法，如果大对象在新生代中经历复制，会带来较高成本。

## 11. 长期存活对象进入老年代

对象在新生代中每熬过一次 Minor GC，年龄通常会加 1。

例如：

```text
经历第 1 次 Minor GC 后仍然存活：年龄 = 1
经历第 2 次 Minor GC 后仍然存活：年龄 = 2
经历第 3 次 Minor GC 后仍然存活：年龄 = 3
```

当对象年龄达到一定阈值时，就会晋升到老年代。

这个阈值可以通过参数控制：

```text
-XX:MaxTenuringThreshold
```

例如默认最大年龄可能是 15，表示对象最多经历多次 Minor GC 后进入老年代。

## 12. 动态对象年龄判定

对象不一定非要等到 `MaxTenuringThreshold` 才进入老年代。

JVM 还会根据 Survivor 区的空间压力，提前让一部分对象晋升到老年代。

规则可以简单理解为：

> 如果 Survivor 区中某个年龄及以下的对象累计大小超过 Survivor 空间的一半，那么年龄大于等于该年龄的对象可以直接进入老年代。

例如：

```text
Survivor 总大小 = 16MB
Survivor 一半 = 8MB

年龄 1 的对象：2MB
年龄 2 的对象：3MB
年龄 3 的对象：4MB
```

从小到大累加：

```text
年龄 1：2MB
年龄 1 + 年龄 2：5MB
年龄 1 + 年龄 2 + 年龄 3：9MB
```

累加到年龄 3 时，已经超过 Survivor 一半。

那么 JVM 可能决定：

```text
年龄 >= 3 的对象直接晋升到老年代
```

即使它们还没达到 `MaxTenuringThreshold`。

这样做的原因是：

```text
Survivor 空间有限
如果很多对象一直留在 Survivor 中，会影响后续 Minor GC
```

一句话记忆：

> 动态年龄判定就是 JVM 根据 Survivor 区压力，提前把一批比较“老”的对象送进老年代。

## 13. 空间分配担保

空间分配担保发生在 Minor GC 前。

Minor GC 主要回收新生代，但回收后可能有一批对象需要晋升到老年代。

问题是：

```text
如果老年代放不下这些晋升对象怎么办？
```

所以 Minor GC 前，JVM 会先检查老年代空间是否足够。

这就叫空间分配担保。

### 13.1 最保守的检查

JVM 会先判断：

```text
老年代可用连续空间 >= 新生代所有对象总大小
```

如果成立，说明肯定安全。

因为即使新生代所有对象都存活，并且全部晋升到老年代，老年代也放得下。

### 13.2 如果放不下整个新生代

如果老年代放不下整个新生代，也不代表一定不能进行 Minor GC。

因为新生代中大多数对象可能会死亡，真正需要晋升的对象可能很少。

此时 JVM 可能参考历史经验：

```text
历次 Minor GC 后晋升到老年代对象的平均大小
```

如果：

```text
老年代最大可用连续空间 > 历史平均晋升大小
```

那么 JVM 可能尝试进行一次 Minor GC。

这次尝试有风险，因为历史平均值不是保证。

## 14. Full GC 和担保失败

### 14.1 Full GC 是什么

Full GC 是一次范围更大的垃圾回收。

简单理解：

```text
Minor GC：
主要回收新生代，发生频繁，速度相对较快。

Full GC：
通常回收整个 Java 堆，至少会涉及老年代，速度较慢，停顿更明显。
```

Full GC 通常会 Stop The World。

可能触发 Full GC 的情况：

- 老年代空间不足。
- Minor GC 后对象晋升失败。
- 方法区或元空间不足。
- 调用了 `System.gc()`，并且 JVM 没有忽略它。

### 14.2 担保失败是什么

担保不是指真的有一个线程或对象做担保，而是 JVM 在 Minor GC 前做的空间风险判断。

担保成功的意思是：

```text
老年代有足够空间接收新生代晋升对象。
```

担保失败的意思是：

```text
Minor GC 后，实际需要晋升的对象太多，老年代放不下。
```

例如：

```text
老年代可用空间：40MB
历史平均晋升大小：20MB

JVM 判断大概率够，于是尝试 Minor GC。
```

但这次 Minor GC 后实际需要晋升：

```text
60MB
```

老年代只有：

```text
40MB
```

放不下，于是出现晋升失败，也就是担保失败。

这种情况下，JVM 通常会触发 Full GC。

一句话记忆：

> 空间分配担保是 Minor GC 前的老年代空间检查；担保失败就是实际晋升对象超过老年代可用空间。

## 15. 整体关系总结

可以把这些知识串成一条线：

```text
对象优先进入 Eden
    ↓
Eden 空间不足，触发 Minor GC
    ↓
存活对象进入 Survivor，年龄增加
    ↓
长期存活对象或大对象进入老年代
    ↓
老年代空间压力变大
    ↓
触发老年代收集器，例如 CMS
    ↓
CMS 并发执行，停顿短，但可能吞吐量低
    ↓
CMS 并发期间会产生浮动垃圾
    ↓
老年代空间不足时可能发生 Concurrent Mode Failure 或 Full GC
```

最终可以这样记：

```text
GC Roots：判断对象是否存活的起点。
新生代：放年轻对象，Minor GC 频繁。
老年代：放长期存活对象，回收成本高。
Parallel Scavenge：关注吞吐量。
CMS：关注低停顿，但吞吐量可能下降。
G1：按 Region 管理内存，通过标记和筛选回收控制停顿。
SATB：记录并发标记期间的引用变化，避免漏标。
空间分配担保：Minor GC 前检查老年代能不能接收晋升对象。
Full GC：范围更大、停顿更明显的垃圾回收。
```
